## 0. How to use this document

### 0.1 Purpose

This document is the single place where the frontend and backend agree on **every endpoint, every JSON shape, every enum, every validation rule and every error**. Each side builds against it independently:

- **Frontend** can write TypeScript types, Zod schemas and a mock server from §1–§9 and §12 without waiting for the backend.
- **Backend** can write DRF serializers, views and tests from the same sections.
- **Both** run the same examples (§12) and fixtures (§13) in CI, so a mismatch fails a build instead of reaching a shop.

### 0.2 Precedence and change rules

1. Order of authority: **SRS v0.5 → SDD v0.4 → this contract → code.** If code and this contract disagree, that is a bug: fix the code or open a PR against this document.
2. The machine-readable OpenAPI file (`contract/openapi.json`, generated by `drf-spectacular`) must match this document. If they differ, this document wins until both are fixed in the same PR.
3. A change to anything in this document needs a PR approved by **one frontend and one backend developer** (§14).
4. Section numbers are stable. Endpoint IDs (`E-01`…) and decision IDs (`CD-01`…) are never reused.

### 0.3 Contract decisions that refine the SDD

Writing exact shapes exposed places where SDD v0.4 was silent or inconsistent. These decisions are **proposed here and must be confirmed by the team**; once confirmed, SDD v0.5 should be updated to match.

| ID | Decision | Reason | SDD section to update |
| --- | --- | --- | --- |
| CD-01 | Physical counts [S] are **operations** (`SubmitCount`, `DecideCount`) sent through `push`. There are no REST endpoints `POST /v1/counts…`. | SDD §6.4 says counts are operations; SDD §7.2 lists REST endpoints. One write path only (ADR-006). | §7.2 |
| CD-02 | `ReviewQuarantine` is **folded into `ResolveConflict`** (resolution kinds `ACCEPT_QUARANTINED`, `REJECT_QUARANTINED`). | One resolution mechanism with one stale-version check. | §6.4, §6.14 |
| CD-03 | A user with **no shop** receives an *onboarding session* (`shopId: null`). `POST /v1/shops` and `POST /v1/invites/{token}/accept` return a **full shop-scoped session** (tokens + lease). | Tokens are shop-scoped (SDD §5.4); a new user has no shop yet. | §7.2, §7.5 |
| CD-04 | If a user has several ACTIVE memberships and sends no `membershipId`, sign-in returns `409 MEMBERSHIP_SELECTION_REQUIRED` with the choices. | SDD D-04 says sign-in selects one. | §7.5 |
| CD-05 | `pull` also returns `actors` (names and roles of shop members) so history can show who did what offline. Dexie gets a small `actors` table. | Review screen shows user names (SDD §9.2). | §5.9, §7.3 |
| CD-06 | The operation envelope gains optional `supersedesOpId` (re-entry of a rejected record, SDD D-10). | Links the new operation to the rejected one. | §6.5 |
| CD-07 | `CancelSale` carries **client-generated IDs for the reversal entries** (`reversals[]`). | Same ID on both sides avoids double counting (SDD INV-09). | §6.13 |
| CD-08 | `ReceiveStock` carries `lines[]` (several products per delivery, atomic). | A delivery usually has several products. | §6.4 |
| CD-09 | `Idempotency-Key` header is **required** on `POST /v1/shops` and `POST /v1/shops/me/invites`. | Safe retry on slow networks. | §7.1 |
| CD-10 | New error codes (§8) for sign-in, invites, closure confirmation and limits. | Frontend needs stable codes for each message. | §7.4 |
| CD-11 | Fields a role may not see are **absent**, never `null`. | `null` means "no value"; absent means "not for you". | §7.3 |
| CD-12 | `payloadHash` is defined precisely (§6.5): SHA-256 of the RFC 8785 canonical JSON of `{"type", "payload"}`, base64url, no padding. | Client and server must hash identically. | §6.5 |
| CD-13 | The envelope field `baseVersions` (SDD §6.5) is **removed**; `baseVersion` lives inside each payload entry. | One place for the value; smaller payloads. | §6.5 |

## 1. Conventions

### 1.1 Transport

| Item | Rule |
| --- | --- |
| Base URL | `https://<api-host>/v1` (configured by `VITE_API_URL`). HTTPS only. |
| Format | JSON, UTF-8, `Content-Type: application/json` (CSV exports excepted). Responses are gzip-compressed when the client sends `Accept-Encoding: gzip`. |
| Method semantics | `GET` is safe and cacheable only where stated; every write is `POST`. There is no `PUT`, `PATCH` or `DELETE`. |
| Time zone | All timestamps are UTC. Business days ("today") are Africa/Addis_Ababa (UTC+3); the client formats, the server only filters. |
| Request timeout | Client uses 70 seconds (covers a cold-starting server). |
| CORS | The server allows only the web origin; no cookies are used. |

### 1.2 Field casing and primitive types

JSON field names are **`camelCase`**. (Django models use `snake_case`; serializers map between them.)

| Name | JSON type | Format and rules | Example |
| --- | --- | --- | --- |
| `Uuid` | string | Canonical lowercase hex with hyphens (36 chars). Client-generated IDs SHOULD be UUIDv7. The server accepts any version but rejects the nil UUID and uppercase forms (`INVALID_FORMAT`). | `"0190f3a1-1001-7000-8000-000000001001"` |
| `IsoTimestamp` | string | `YYYY-MM-DDTHH:mm:ss.sssZ`, always UTC, always `Z`. Client may omit milliseconds when sending; server always returns them. | `"2026-10-12T08:14:03.250Z"` |
| `IsoDate` | string | `YYYY-MM-DD` (an Addis Ababa calendar day) | `"2026-10-12"` |
| `Santim` | integer | Money in santim (1 ETB = 100 santim). `0 … 99_999_999_999` for prices and costs; totals up to `9_007_199_254_740_991`. | `12500` = ETB 125.00 |
| `QtyMilli` | integer | Quantity in thousandths of the unit. Quantities in a sale or receipt: `1 … 999_999_999`. Deltas and stock levels may be negative. | `7000` = 7 kg or 7 pieces |
| `Seq` | integer | Server-assigned, increasing per shop (change log sequence). | `4821` |
| `Version` | integer | Per-product stock version, +1 per accepted ledger entry. | `3` |
| `Hash` | string | SHA-256, base64url, no padding (43 chars) | `"Zx3…"` |
| `Text` | string | NFC-normalised, trimmed, no control characters (including newlines unless stated) | |

```ts
export type Uuid = string;
export type IsoTimestamp = string;
export type IsoDate = string;
export type Santim = number;
export type QtyMilli = number;
export type Seq = number;
export type Version = number;
export type Hash = string;
```

**Numbers are always JSON integers.** Never floats, never strings, never exponent notation. Any value that would exceed `9_007_199_254_740_991` is rejected, so JavaScript can read every number exactly.

**Quantities by unit.** The product's `unit` fixes the allowed precision:

| Unit | Decimals | `qtyMilli` rule | Example |
| --- | --- | --- | --- |
| `PIECE`, `PACK` | 0 | multiple of 1000 | `3000` = 3 pieces |
| `KG`, `GRAM`, `LITRE`, `MILLILITRE` | up to 3 | any integer | `250` = 0.250 kg |

**Line total:** `round_half_up(qtyMilli × unitPriceSantim ÷ 1000)`. **Sale total:** sum of the rounded line totals. The server recomputes both; a client total that differs is rejected (§9).

### 1.3 Null, absent and unknown fields

| Case | Rule |
| --- | --- |
| Optional value with no data (response) | `null` |
| Field the caller's role may not see | **absent** (CD-11). Clients must treat absent owner-only fields as "not available", never as zero. |
| Optional field (request) | May be omitted or `null`, same meaning, except in `UpdateProduct.changes` (§6.7.2): omitted = unchanged, `null` = clear. |
| Unknown fields in a **request** | Rejected with `VALIDATION_FAILED` / `UNKNOWN_FIELD`. (An old server must not silently drop data from a new client.) |
| Unknown fields in a **response** | Clients MUST ignore them. New response fields are non-breaking (§14). |
| Array order | Preserved as sent or documented. Pull entity arrays carry no ordering guarantee except where stated. |

### 1.4 Headers

| Header | Direction | Rule |
| --- | --- | --- |
| `Authorization: Bearer <token>` | request | Access token, or `drainToken` on sync endpoints only (§5.3). Required on every endpoint except those marked *Public*. |
| `Content-Type: application/json` | request | Required on requests with a body. |
| `Idempotency-Key: <uuid>` | request | **Required** on `POST /v1/shops` and `POST /v1/shops/me/invites`; stored 24 hours. Same key + same body returns the first response; same key + different body returns `409 IDEMPOTENCY_KEY_REUSE`. Sync operations use `opId` instead. |
| `X-Request-Id` | both | Client MAY send a UUID; server always returns one (also inside every error body as `requestId`). Quote it in bug reports. |
| `Retry-After` | response | Seconds, on `429` and `503`. |
| `Content-Disposition` | response | On CSV exports (§7.5). |

### 1.5 Error format (RFC 9457 problem+json)

Every non-2xx response, and every per-operation rejection inside a `200`, uses this shape. Content type: `application/problem+json`.

```ts
export interface Problem {
  type: string;            // "urn:stokari:problem:<CODE>"
  title: string;           // short English text, for developers
  status: number;          // HTTP status (also present for per-operation results)
  code: ErrorCode;         // stable machine code, see §8. The frontend switches on this.
  detail?: string;         // English explanation, never shown verbatim to users
  fieldErrors?: FieldError[];
  requestId: string;
  // extensions, only on specific codes (§8):
  drainToken?: string; drainTokenExpiresAt?: IsoTimestamp;     // ACCOUNT_DEACTIVATED
  memberships?: MembershipChoice[];                             // MEMBERSHIP_SELECTION_REQUIRED
  warnings?: ClosureWarnings;                                   // CONFIRMATION_REQUIRED
  retryAfterSeconds?: number;                                   // RATE_LIMITED
}
export interface FieldError {
  field: string;           // dotted path with indexes, e.g. "lines[0].qtyMilli"
  code: FieldErrorCode;
  message: string;         // English, developer-facing
}
export type FieldErrorCode =
  | 'REQUIRED' | 'INVALID_TYPE' | 'INVALID_FORMAT' | 'OUT_OF_RANGE' | 'INVALID_PRECISION'
  | 'TOO_SHORT' | 'TOO_LONG' | 'UNKNOWN_FIELD' | 'NOT_ALLOWED' | 'MISMATCH'
  | 'UNKNOWN_REFERENCE' | 'DUPLICATE';
```

**Three kinds of failure must stay distinct** (SRS §9.2): *transport failure* (no response; retry with the same `opId`), *business rejection* (a `REJECTED` result or a 4xx problem; do not retry unchanged), and *accepted but acknowledgment lost* (resolved by retrying the same `opId` or querying status, §6.3).

User-facing text is **never taken from the server**. The frontend maps `code` (and `reasonCode`) to translated messages (`i18n/en.json`, `am.json`).

### 1.6 Pagination

List endpoints use opaque cursors unless stated.

| Parameter | Rule |
| --- | --- |
| `cursor` | Opaque string from the previous `nextCursor`; omit for the first page. |
| `limit` | Integer, default 50, max 200. (`pull` is different, §6.2.) |

Response: `{ "items": [...], "nextCursor": "…" | null }`. `nextCursor: null` means the last page.

### 1.7 Limits

| Limit | Value | Error |
| --- | --- | --- |
| Operations per push | 1 – 50 | `BATCH_TOO_LARGE` (400) |
| Push body size | ≤ 200 KB | `PAYLOAD_TOO_LARGE` (413) |
| Lines per sale / receipt | 1 – 100 | `VALIDATION_FAILED` / `OUT_OF_RANGE` |
| `opIds` per status query | 1 – 100 | `VALIDATION_FAILED` |
| Product `name` / `nameAlt` | 1 – 120 chars (after trim), at least one of the two present | `TOO_SHORT` / `TOO_LONG` |
| `reason`, `note` | 1 – 500 chars (`note` may be empty or null where optional) | `TOO_LONG` |
| Attendants per shop | 5 active | `ATTENDANT_LIMIT_REACHED` (409) |
| Access token | 15 minutes | |
| Refresh token | up to 30 days, rotated on every use | |
| Offline lease | up to 7 days | |
| Drain token | 10 minutes | |
| Invite | valid 7 days, single use | `INVITE_INVALID` |
| Nonce | valid 5 minutes, single use | `NONCE_INVALID` |
| Rate limits | push/pull 60 req/min/user; auth 10 req/min/IP | `RATE_LIMITED` (429) |

### 1.8 Roles and field visibility

Roles: `OWNER`, `ATTENDANT`. A platform administrator has no shop membership and can call **no** shop endpoint. **Owner-only data** (never sent to attendants, in any endpoint, pull or export): `Product.costSantim`, `StockChange.unitCostSantim`, inventory valuation, `conflicts`, quarantined operation details, member emails, notifications.

### 1.9 Example cast (used in every example)

All examples in this document use the same data so frontend and backend can paste them into tests.

| Name | Value |
| --- | --- |
| Shop `shopId` | `0190f3a1-2b4c-7d5e-8f60-1a2b3c4d5e6f` |
| Owner user / membership | `0190f3a1-0001-7000-8000-000000000001` / `0190f3a1-0011-7000-8000-000000000011` |
| Attendant user / membership | `0190f3a1-0002-7000-8000-000000000002` / `0190f3a1-0012-7000-8000-000000000012` |
| Device A (attendant) / Device B (attendant) | `0190f3a1-00a1-7000-8000-0000000000a1` / `0190f3a1-00b1-7000-8000-0000000000b1` |
| Product Sugar (`KG`, price 12500) | `0190f3a1-1001-7000-8000-000000001001` |
| Product Rice (`KG`, price 8000) | `0190f3a1-1002-7000-8000-000000001002` |
| Story | Sugar opens at 10 kg. Device A sells 7 kg offline, Device B sells 6 kg offline. Device B's sale goes to review (SRS AT-06). |

## 3. Data structures (wire shapes)

These are the shapes returned by the API and carried in `pull`. They are identical on both sides. Field comments marked **OWNER** are absent for attendants (§1.3, CD-11).

### 3.1 Who sets what

| Kind of value | Set by | Notes |
| --- | --- | --- |
| `id` of records the client creates (product, sale, sale line, stock change, count) | **Client** (UUIDv7) | Same ID locally and on the server. Never regenerated on retry. |
| `opId` | **Client**, once per operation | Stable across every retry. |
| `receivedAt`, `serverSeq`, `appliedVersion`, `postedStatus`, `updatedSeq`, `version`, `underReview` | **Server** | Client never sends them. |
| `clientCreatedAt`, `baseVersion` | Client | Evidence and display only; never authority (INV-11). |
| `userId`, `deviceId` on a record | Server (from the token and push header) | Client-supplied values are ignored. |
| Immutable once stored | `StockChange`, `Sale`, `SaleLine`, `SaleCancellation` | There is no endpoint to change them. A mistake is fixed by a new operation. |
| Mutable master data | `Product` fields (last writer wins by server order), `ConflictCase` | |

### 3.2 Auth and session

```ts
export interface SessionInfo {
  userId: Uuid;
  email: string;
  name: string;
  shopId: Uuid | null;            // null in an onboarding session (user has no shop yet)
  membershipId: Uuid | null;
  role: Role | null;
}
export interface LeaseInfo {
  leaseId: Uuid;                  // sent back in every push that contains OFFLINE_COMPLETED operations
  token: string;                  // signed lease JWT; opaque to the client, stored in meta.lease
  issuedAt: IsoTimestamp;
  expiresAt: IsoTimestamp;        // at most issuedAt + 7 days
  allowedOps: OperationType[];    // what this role may create offline
}
export interface AuthSession {
  accessToken: string;            // JWT, 15 min; opaque to the client, keep in memory only
  accessTokenExpiresAt: IsoTimestamp;
  refreshToken: string;           // random, rotated on every use; stored in IndexedDB (SDD D-02)
  refreshTokenExpiresAt: IsoTimestamp;
  session: SessionInfo;
  lease: LeaseInfo | null;        // null for an onboarding session
  serverTime: IsoTimestamp;       // use to set meta.clockOffset
}
export interface MembershipChoice { membershipId: Uuid; shopId: Uuid; shopName: string; role: Role; }
```

`allowedOps` by role: **Attendant** → `["RecordSale"]`. **Owner** → every `OperationType` the shop's build supports (`SubmitCount` and `DecideCount` only if counts are built).

### 3.4 Product and stock

```ts
export interface Product {
  id: Uuid;
  name: string | null;            // at least one of name / nameAlt is non-null
  nameAlt: string | null;         // second language, e.g. Amharic; independent of the UI language (FR-35)
  unit: Unit;                     // immutable after creation
  priceSantim: Santim;
  costSantim?: Santim | null;     // OWNER. null = unknown cost
  lowStockMilli: QtyMilli;        // 0 = no alert
  status: ProductStatus;
  updatedSeq: Seq;
}
// Display name rule (both sides): name ?? nameAlt.

export interface StockLevelView {
  productId: Uuid;
  qtyMilli: QtyMilli;             // may be negative (recorded oversell)
  version: Version;
  underReview: boolean;           // true while an open stock case references the product
}

export interface StockChange {                             // immutable ledger entry
  id: Uuid;
  opId: Uuid;
  productId: Uuid;
  type: StockChangeType;
  deltaMilli: QtyMilli;           // signed, never 0
  adjustmentReason: AdjustmentReason | null;   // required when type = ADJUSTMENT
  note: string | null;
  unitCostSantim?: Santim | null; // OWNER, RECEIPT entries
  saleId: Uuid | null;            // SALE and SALE_CANCELLATION
  reversesId: Uuid | null;        // SALE_CANCELLATION -> id of the original SALE entry
  countSessionId: Uuid | null;    // COUNT_CORRECTION [S]
  conflictCaseId?: Uuid | null;   // OWNER; set on entries created by a resolution
  userId: Uuid;
  deviceId: Uuid;
  clientCreatedAt: IsoTimestamp;
  receivedAt: IsoTimestamp;
  baseVersion: Version;           // what the device knew
  appliedVersion: Version;        // what the server applied (contiguous per product)
  serverSeq: Seq;
  postedStatus: PostedStatus;     // fixed at insert
  effectiveStatus: EffectiveStatus; // NEEDS_REVIEW while its case is OPEN, RESOLVED after, else POSTED
}
```

**Invariant both sides can rely on (INV-03):** for every product, `StockLevelView.qtyMilli` equals the sum of `deltaMilli` of its `StockChange` rows, and `version` equals their count. (The client holds a pending part on top; see SDD §5.10.)

### 3.5 Sales

```ts
export interface SaleLine {
  id: Uuid;
  productId: Uuid;
  qtyMilli: QtyMilli;             // 1 … 999_999_999
  unitPriceSantim: Santim;        // snapshot of the price charged; later price edits never change it
  lineTotalSantim: Santim;
}
export interface Sale {                                    // immutable
  id: Uuid;
  opId: Uuid;
  userId: Uuid;
  deviceId: Uuid;
  paymentLabel: PaymentLabel;
  totalSantim: Santim;            // = sum of lineTotalSantim
  clientCreatedAt: IsoTimestamp;  // business time, shown in EAT
  receivedAt: IsoTimestamp;
  lines: SaleLine[];              // 1 – 100
}
export interface SaleCancellation {                        // at most one per sale
  saleId: Uuid;
  opId: Uuid;
  reason: string;
  cancelledBy: Uuid;
  at: IsoTimestamp;
}
```

A sale is **cancelled** iff a `SaleCancellation` with its `saleId` exists. A sale **needs review** iff any of its `SALE` stock changes has `effectiveStatus = NEEDS_REVIEW`. Neither is a field on `Sale`.

### 3.6 Conflict cases (OWNER only)

```ts
export interface ConflictItem { itemType: 'STOCK_CHANGE' | 'SALE' | 'OPERATION'; itemId: Uuid; }
export interface QuarantinedOperationSummary {
  opId: Uuid;
  type: OperationType;
  userId: Uuid;
  deviceId: Uuid;
  clientCreatedAt: IsoTimestamp;
  reasonCode: ReviewReasonCode;
  decision: QuarantineDecision;
  summary: { saleTotalSantim?: Santim; lineCount?: number; productId?: Uuid; deltaMilli?: QtyMilli };
}
```

### 5.2 E-03 `POST /v1/auth/google`

*Public.* Exchanges a Google ID token for a Stokari session. **First sign-in on a device needs internet.**

```ts

  nonce: string;            // the value from E-02, must equal the token's nonce claim

```

| Situation | Result |
| --- | --- |
| Exactly one ACTIVE membership | `200` `AuthSession` with `session.shopId`, role, and a `lease` |
| No membership | `200` **onboarding** `AuthSession`: `shopId`, `membershipId`, `role` all `null`, `lease: null` (CD-03) |
| Several ACTIVE memberships, no `membershipId` | `409 MEMBERSHIP_SELECTION_REQUIRED` with `memberships[]`; the client shows a picker and repeats the call with the chosen `membershipId` (with a **new** nonce) |
| Only membership is DEACTIVATED | `403 ACCOUNT_DEACTIVATED` with `drainToken` (§5.3) |
| Invalid, expired, wrong-audience or unverified-email Google token | `401 GOOGLE_TOKEN_INVALID` |
| Nonce unknown, used or expired | `401 NONCE_INVALID` |

Server side: verifies signature, audience, issuer, expiry, `email_verified`, nonce; finds or creates the user by Google `sub`; registers the device; creates a refresh token (hashed) and, for shop sessions, an offline lease. Stokari, not Google, decides what the user may do.

### 5.3 E-04 `POST /v1/auth/refresh`

*Refresh token in body.* Rotates the refresh token. The old token stops working immediately.

```ts
export interface RefreshRequest { refreshToken: string; deviceId: Uuid; }
// 200 -> AuthSession, with lease: null (keep the stored lease; renew with E-05)
```

| Situation | Result |
| --- | --- |
| Valid | `200` `AuthSession` (new `refreshToken`) |
| Unknown or expired token, or wrong device | `401 REFRESH_TOKEN_INVALID` |
| A **rotated** (already used) token is presented again | `401 REFRESH_TOKEN_REUSED`; the whole token family is revoked; the user must sign in again |
| Membership deactivated | `403 ACCOUNT_DEACTIVATED` with **`drainToken` and `drainTokenExpiresAt`** |

**Drain token.** A 10-minute token with a narrow purpose: it is accepted **only** by E-14 (`push`) and E-16 (`status`), it cannot read data, and every operation sent with it is quarantined (`reasonCode: "DRAIN"`), never applied. It exists so a deactivated attendant's pending records are preserved for the owner's review (SRS FR-04). Use it as `Authorization: Bearer <drainToken>`. After the push, the client clears credentials but **keeps local business records** (INV-12).

### 5.6 Session lifecycle rules (both sides)

```text
first run        -> deviceId generated, stored in meta.deviceId
sign in          -> E-02, Google, E-03
                    onboarding session?  -> E-07 (create shop) or E-11 (accept invite) -> shop session
every ~14 min    -> E-04 (refresh) before the 15-minute access token expires, or on 401 once
online + lease   -> E-05 when the lease has < 24 h left
logout           -> E-06; clear credentials, keep data
deactivated      -> E-04 or E-03 gives 403 + drainToken -> E-14 with drainToken -> clear credentials
```

An **onboarding session** is accepted only by E-04, E-06, E-07 and E-11. Any other endpoint returns `403 SHOP_REQUIRED`. Shop-scoped sessions are bound to exactly one membership; the shop always comes from the token, **never from a header or body** (FR-07).

## 6. Sync endpoints and operations

### 6.1 E-14 `POST /v1/sync/push`

*Member or drain token.* The only write endpoint. Sends a batch of operations; returns one result per operation.

```ts
export interface PushRequest {
  protocolVersion: number;       // 1. Unsupported -> 426 UPGRADE_REQUIRED
  schemaVersion: number;         // the device's local Dexie schema version; too old -> 426
  deviceId: Uuid;                // must equal the device in the access token -> else 403 DEVICE_MISMATCH
  leaseId?: Uuid;                // REQUIRED if any operation has mode OFFLINE_COMPLETED
  ops: OperationEnvelope[];      // 1-50 items, body <= 200 KB, strictly increasing deviceSeq
}
export interface PushResponse {
  serverTime: IsoTimestamp;
  results: OperationResult[];    // SAME length and order as the request ops
}
```

**HTTP semantics.** `200` means *the batch was processed*; individual operations may still be `REJECTED`. Request-level failures (nothing processed): `400 VALIDATION_FAILED` (bad envelope, unknown `type`, `deviceSeq` not increasing, duplicate `opId` is **not** an error: see below), `400 BATCH_TOO_LARGE`, `413 PAYLOAD_TOO_LARGE`, `401`, `403 ACCOUNT_DEACTIVATED` / `DEVICE_MISMATCH` / `SHOP_REQUIRED`, `426 UPGRADE_REQUIRED`, `429 RATE_LIMITED`, `5xx`.

**Processing rules (server).**
1. Operations are processed **one by one in array order**, each in its own transaction. One invalid operation never rolls back the others.
2. An `opId` already processed with the same `payloadHash` returns the **stored result** with `replayed: true` (no second effect). The same `opId` with a different hash returns `REJECTED` / `IDEMPOTENCY_KEY_REUSE`. A duplicate `opId` inside one batch is handled the same way (second occurrence is a replay).
3. `dependsOn`: if a listed operation was `REJECTED`/`REJECTED_DEPENDENCY` the dependent gets `REJECTED_DEPENDENCY`; if it was `QUARANTINED` the dependent is `QUARANTINED` into the same case.
4. Shop, user and role always come from the token. Anything the client sends about them is ignored.
5. Drain token: every operation is `QUARANTINED` (`reasonCode: "DRAIN"`), none applied (§6.9).

**Client rules.**
- Send operations in ascending `deviceSeq`; stop at the first transport failure.
- After any transport failure or timeout: **retry the same operation with the same `opId`** or query E-16. Never create a new `opId` for the same user action.
- Apply each result to local state in **one Dexie transaction** (SDD §5.10).

### 6.2 E-15 `GET /v1/sync/pull`

*Member.* Returns changes after a cursor, in order. **A new device bootstraps by pulling from `cursor=0` until `hasMore` is false.**

| Query | Rule |
| --- | --- |
| `cursor` | Integer ≥ 0, default 0. The `nextCursor` from the previous page. |
| `limit` | Default 200, max 500 (number of change-log rows scanned, not entities returned). |

```ts
export interface PullResponse {
  nextCursor: Seq;                 // store it in the SAME Dexie transaction that applies the page
  hasMore: boolean;
  headSeq: Seq;                    // newest sequence on the server; progress = nextCursor / headSeq
  serverTime: IsoTimestamp;
  products: Product[];
  stockChanges: StockChange[];
  stockLevels: StockLevelView[];
  sales: Sale[];
  saleCancellations: SaleCancellation[];
  actors: Actor[];
  conflicts?: ConflictCase[];      // OWNER only; absent for attendants
}
```

**Rules.**
- Arrays are always present (possibly empty), except `conflicts` for attendants.
- Each entity is its **current** state. Apply by **upsert keyed by id** (`productId` for `stockLevels`, `saleId` for `saleCancellations`). Because ledger rows keep the same `id` locally and on the server, a pending local entry is replaced by its confirmed version, never duplicated.
- Apply a `stockLevels` entry only if its `version` is greater than the local `confirmedVersion`.
- `conflicts` entries replace the local case entirely.
- `nextCursor` is the last change-log sequence scanned, never a timestamp. If `hasMore` is true, call again with `cursor = nextCursor`.
- `409 CURSOR_RESET`: the cursor is invalid; restart from `cursor=0` **without touching the outbox**.
- After the last bootstrap page the device is "ready" only when the local integrity check passes (`confirmedQty` equals the sum of local confirmed entries).

### 6.5 Operation envelope and `payloadHash`

```ts
export interface EnvelopeBase {
  opId: Uuid;                       // once per user action; identical on every retry
  deviceSeq: number;                // integer >= 1, strictly increasing per device; defines causal order
  mode: OperationMode;
  dependsOn?: Uuid[];               // opIds that must be accepted first (e.g. CancelSale -> RecordSale)
  supersedesOpId?: Uuid;            // re-entry of a rejected record (CD-06)
  clientCreatedAt: IsoTimestamp;    // display and routing hint only
  payloadHash: Hash;
}
export type OperationEnvelope =
  | (EnvelopeBase & { type: 'CreateProduct'; payload: CreateProductPayload })
  | (EnvelopeBase & { type: 'UpdateProduct'; payload: UpdateProductPayload })
  | (EnvelopeBase & { type: 'SetProductStatus'; payload: SetProductStatusPayload })
  | (EnvelopeBase & { type: 'RecordSale'; payload: RecordSalePayload })
  | (EnvelopeBase & { type: 'CancelSale'; payload: CancelSalePayload })
  | (EnvelopeBase & { type: 'ReceiveStock'; payload: ReceiveStockPayload })
  | (EnvelopeBase & { type: 'AdjustStock'; payload: AdjustStockPayload })
  | (EnvelopeBase & { type: 'ResolveConflict'; payload: ResolveConflictPayload })
  | (EnvelopeBase & { type: 'SubmitCount'; payload: SubmitCountPayload })
  | (EnvelopeBase & { type: 'DecideCount'; payload: DecideCountPayload });
```

The envelope has **no** `shopId`, `userId`, `role` or totals-from-server fields. (The SDD's envelope field `baseVersions` is removed: `baseVersion` lives inside the payload entries, CD-13.)

**`payloadHash` (CD-12).** Detects local corruption and `opId` reuse with a different payload.

```text
input  = RFC 8785 (JCS) canonical JSON of the object { "type": <type>, "payload": <payload> }
hash   = base64url( SHA-256( UTF-8(input) ) )   without "=" padding   -> 43 characters
```

Not part of the hash: `opId`, `deviceSeq`, `mode`, `dependsOn`, `supersedesOpId`, `clientCreatedAt`. That way changing `mode` or adding `dependsOn` never changes the hash of the same action. All keys are ASCII camelCase and all numbers are integers, so ordinary "sort keys, no whitespace" JSON serialization equals JCS in both languages. **Both sides must pass the vectors in `fixtures/payload-hash-vectors.json`** (§13). A mismatch on the server returns `REJECTED` / `PAYLOAD_INTEGRITY`.

```ts
// web
const bytes = new TextEncoder().encode(canonicalize({ type, payload }));
const hash = base64url(new Uint8Array(await crypto.subtle.digest('SHA-256', bytes)));
```
```python
# api
digest = hashlib.sha256(
    json.dumps(
        {"type": t, "payload": p}, sort_keys=True, separators=(",", ":"), ensure_ascii=False
    ).encode("utf-8")
).digest()
h = base64.urlsafe_b64encode(digest).rstrip(b"=").decode()
```

### 6.6 Operation results

```ts
export interface AppliedEntry {
  changeId: Uuid;                   // the client's own stockChange id
  productId: Uuid;
  appliedVersion: Version;
  serverSeq: Seq;
  postedStatus: PostedStatus;
}
export interface OperationResult {
  opId: Uuid;
  outcome: OperationOutcome;
  effectApplied: boolean;           // did stock or records actually change?
  replayed?: boolean;               // true when this is a stored result for a retried opId
  noop?: boolean;                   // true when already applied (second cancel, already-resolved case)
  code?: ErrorCode;                 // REJECTED / REJECTED_DEPENDENCY: why (stable code)
  detail?: string;                  // English, developer-facing
  fieldErrors?: FieldError[];       // REJECTED with VALIDATION_FAILED
  reasonCode?: ReviewReasonCode;    // NEEDS_REVIEW / QUARANTINED: why
  conflictCaseId?: Uuid;            // NEEDS_REVIEW / QUARANTINED
  dependsOnOpId?: Uuid;             // REJECTED_DEPENDENCY: the operation that failed
  entries?: AppliedEntry[];         // ledger entries created by this operation
  stockAfter?: StockLevelView[];    // authoritative levels for touched products
  inner?: { opId: Uuid; outcome: OperationOutcome; code?: ErrorCode }[];   // ResolveConflict ACCEPT_QUARANTINED only
}
```

| Outcome | Meaning | Present fields | What the client does |
| --- | --- | --- | --- |
| `ACCEPTED` | Applied; invariants hold | `effectApplied: true`, `entries`, `stockAfter` (or `noop: true`) | Mark `SYNCED`; update the **same** local rows with `serverSeq`/`appliedVersion`; set confirmed stock from `stockAfter` if newer |
| `NEEDS_REVIEW` | Applied **and** flagged (e.g. offline oversell) | `effectApplied: true` (or `false` for a stale resolution), `reasonCode`, `conflictCaseId`, `entries`, `stockAfter` | Mark `NEEDS_REVIEW`; show the review badge; owner is notified by the server |
| `QUARANTINED` | Held in full, **no** stock or sales effect | `effectApplied: false`, `reasonCode`, `conflictCaseId` | Mark `NEEDS_REVIEW` with the "awaiting authorization review" text; remove its rows from the pending stock delta; keep the record visible |
| `REJECTED` | Not applied; the intent is preserved | `effectApplied: false`, `code`, `detail`, `fieldErrors?` | Mark `REJECTED`; keep for inspection and export; offer "re-enter as new" |
| `REJECTED_DEPENDENCY` | Not applied because an operation it depends on failed | `effectApplied: false`, `code: "DEPENDENCY_REJECTED"`, `dependsOnOpId` | Mark `REJECTED` |

Result details per operation type and situation: §6.7 and the outcome matrix in SDD §6.8.

#### 6.7.1 `CreateProduct`

```ts
export interface CreateProductPayload {
```

#### 6.7.8 `ResolveConflict`

One mechanism resolves every kind of case (CD-02). It carries the `caseVersion` the owner saw.

```ts
export interface ReconcileEntry {
  changeId: Uuid;
  productId: Uuid;
  type: 'RECEIPT' | 'ADJUSTMENT';
  deltaMilli: QtyMilli;             // RECEIPT: > 0. ADJUSTMENT: signed, not 0
  reason?: AdjustmentReason;        // REQUIRED for ADJUSTMENT
  note?: string | null;
  unitCostSantim?: Santim | null;   // RECEIPT only
}
export type Resolution =
  | { kind: 'RECONCILE_STOCK'; entries: ReconcileEntry[] }                           // 1 - 20 entries
  | { kind: 'CANCEL_SALE'; saleId: Uuid; reason: string; reversals: ReversalInput[] }
  | { kind: 'ACKNOWLEDGE'; note?: string | null }
  | { kind: 'ACCEPT_QUARANTINED'; opIds: Uuid[] }                                    // pending quarantined ops of THIS case
  | { kind: 'REJECT_QUARANTINED'; opIds: Uuid[]; reason: string }
  | { kind: 'KEEP_OPEN'; note: string };                                              // records a note, changes no status
export interface ResolveConflictPayload { caseId: Uuid; caseVersion: number; resolution: Resolution; }
```

Which resolutions fit which case type (otherwise `REJECTED` / `RESOLUTION_INVALID`):

| Case type | Valid resolution kinds |
| --- | --- |
| `OFFLINE_OVERSELL` | `RECONCILE_STOCK`, `CANCEL_SALE`, `KEEP_OPEN` |
| `PRODUCT_INACTIVE` | `ACKNOWLEDGE`, `KEEP_OPEN` |
| `AUTHORIZATION_REVIEW`, `INVALID_STOCK_OPERATION`, `CANCELLATION_CONFLICT` | `ACCEPT_QUARANTINED`, `REJECT_QUARANTINED`, `KEEP_OPEN` |

| Situation | Outcome |
| --- | --- |
| `caseVersion` equals the case's version and the resolution is valid | `ACCEPTED`; case → `RESOLVED`; `underReview` cleared when no other open stock case remains; for `OFFLINE_OVERSELL` the product's resulting balance must be ≥ 0 (else `REJECTED` / `RESOLUTION_INVALID`, case stays open) |
| `caseVersion` is older than the case | `NEEDS_REVIEW` / `STALE_RESOLUTION`, `effectApplied: false`; the case stays `OPEN` and gets a `STALE_RESOLUTION` event; the owner must look again |
| Case already `RESOLVED` | `ACCEPTED` + `noop: true` |
| `ACCEPT_QUARANTINED` | Each listed operation is processed through its normal handler **as its original actor**; per-operation results are returned in `inner[]` (they may themselves be `NEEDS_REVIEW` or `REJECTED`) |

A resolution is **a new auditable operation**; it never rewrites the original sale or ledger entries. Offline, it is pending until accepted.

```json
{
  "opId": "0191a2f0-0008-7000-8000-000000000008", "deviceSeq": 8, "type": "ResolveConflict",
  "mode": "OFFLINE_COMPLETED", "clientCreatedAt": "2026-10-12T12:00:00.000Z",
  "payloadHash": "GfD0W0wh2nP3h-rZRpZoxdvaT8vOQ8MF9PVcZzYeLfU",
  "payload": {
    "caseId": "0191b7c0-0c01-7000-8000-000000000c01", "caseVersion": 1,
    "resolution": { "kind": "RECONCILE_STOCK", "entries": [{
      "changeId": "0191a2f0-c008-7000-8000-00000000c008", "productId": "0190f3a1-1001-7000-8000-000000001001",
      "type": "RECEIPT", "deltaMilli": 3000, "note": "Found 3 kg in storage" }] }
  }
}
```

Result addition used by this operation (field on `OperationResult`): `inner?: { opId: Uuid; outcome: OperationOutcome; code?: ErrorCode }[]`.

### 6.8 Ordering and dependencies (client rules)

| Rule | Detail |
| --- | --- |
| Order | The outbox is sent in ascending `deviceSeq`. The server preserves that order. |
| `dependsOn` | Set it when an operation refers to a record whose own operation is **not yet `SYNCED`**: `CancelSale` → the `RecordSale`; any operation on a product → that product's `CreateProduct`; `ResolveConflict` needs none. |
| Failure of a dependency | `REJECTED_DEPENDENCY` (or quarantined into the same case). The dependent record stays visible locally. |
| Re-entry | A rejected record is never retried unchanged. "Re-enter as new" creates a **new** `opId` and sets `supersedesOpId` to the rejected one. |
| Online-mode operations | Create **no** local sale or ledger rows until the server accepts. The outbox row exists; the UI shows "awaiting confirmation". |
| Never switch mode | Once an `ONLINE_CONFIRMATION_REQUIRED` operation has been sent, it is never converted to `OFFLINE_COMPLETED` (risk of a duplicate real-world sale). |

### 6.9 Drain mode (deactivated users)

With a drain token (§5.3): only E-14 and E-16 are allowed; every operation returns `QUARANTINED` with `reasonCode: "DRAIN"` and `effectApplied: false`; the server creates an `AUTHORIZATION_REVIEW` case and notifies the owner. The owner then resolves with `ACCEPT_QUARANTINED` (the operation is applied as the original actor through the normal rules) or `REJECT_QUARANTINED` (with a reason; the record stays visible and exportable).

## 9. Shared validation rules

Both sides implement these identically. The server returns **all** field errors at once.

| Rule | Detail | `FieldErrorCode` |
| --- | --- | --- |
| Required fields | Missing or `null` where not nullable | `REQUIRED` |
| Types | Integers only for money, quantities, versions; strings for text; no booleans-as-strings | `INVALID_TYPE` |
| IDs | Canonical lowercase UUID, not nil | `INVALID_FORMAT` |
| Timestamps | `YYYY-MM-DDTHH:mm:ss(.sss)Z` | `INVALID_FORMAT` |
| Text | Trimmed, NFC, no control characters; lengths per §1.7 | `TOO_SHORT`, `TOO_LONG` |
| Money | `priceSantim`, `costSantim`, `unitPriceSantim`, `unitCostSantim`: `0 … 99_999_999_999` | `OUT_OF_RANGE` |
| Quantities in sales and receipts | `1 … 999_999_999` | `OUT_OF_RANGE` |
| Precision by unit | `PIECE`/`PACK`: multiple of 1000; others: any integer | `INVALID_PRECISION` |
| Deltas | Signed, never 0 | `OUT_OF_RANGE` |
| Totals | `totalSantim` equals the server's recomputation | `MISMATCH` |
| Collections | `lines` 1–100; no repeated `productId` in one sale or receipt | `OUT_OF_RANGE`, `DUPLICATE` |
| References | Product, sale, case, count must exist in the caller's shop | `UNKNOWN_REFERENCE` |
| Immutable fields | `unit` cannot change | `NOT_ALLOWED` |
| Unknown properties | Rejected | `UNKNOWN_FIELD` |
| Cross-field | `name`/`nameAlt` at least one; `openingChangeId` iff `openingQtyMilli > 0`; ADJUSTMENT needs a reason | `REQUIRED`, `NOT_ALLOWED` |

Shared test vectors for money and quantity are in §13. Never use floating point for money or quantities in either language.

## 14. Working agreement and change management

### 14.1 Breaking and non-breaking changes

| Change | Kind | Rule |
| --- | --- | --- |
| New endpoint; new optional response field; new enum value in a response; new optional request field with a safe default | Non-breaking | Minor contract version. Clients ignore unknown fields and enum values. |
| Removing or renaming anything; changing a type, unit or meaning; making an optional request field required; new required request field; changing outcome semantics; changing the hash input | **Breaking** | Major contract version **and** `protocolVersion` bump; the API accepts the previous protocol for one release (`426` otherwise). |
| Changing validation limits | Breaking if stricter; non-breaking if looser | Announce in the PR. |

### 14.2 Process

1. Open a PR against this document **first** (or together with the code). Describe the shape change and show an example.
2. One frontend and one backend reviewer approve. The PR links the SRS requirement or SDD section.
3. Backend regenerates `openapi.json` and fixtures; frontend bumps `contract.lock` and regenerates types.
4. Both contract-test suites (§13.4) must pass before merge.
5. Anything unclear is decided **in this document**, not in chat. If chat decided it, write it here.

## Appendix A. Quick reference

**Core flow in one paragraph.** The device writes locally first, then sends operations with a stable `opId` through `POST /v1/sync/push`; the server answers each with an outcome; the device applies results in one local transaction, then calls `GET /v1/sync/pull` with its cursor to receive everyone's changes. Retries reuse the same `opId`. Offline sales are never rejected for low stock; they are kept and flagged (`NEEDS_REVIEW`) for the owner. Owner-only fields never reach attendants. Money is integer santim, quantities are integer milli-units, and both sides prove identical arithmetic with shared vectors.

**Outcome → client state:** `ACCEPTED` → synced · `NEEDS_REVIEW` / `QUARANTINED` → needs review · `REJECTED` / `REJECTED_DEPENDENCY` → rejected (kept, exportable, re-enter as new).

**Never do:** send shop or role from the client · create a new `opId` on retry · switch an online-mode operation to offline · trust client totals · use floats · show server text to users · purge unsynchronized local records.
